# 方法说明

## 目的

本文档解释 FitLog Local 为什么使用当前的饮食、碳水策略和运动消耗算法。它面向想先理解 App 方法逻辑、再信任数字的用户。

FitLog 是记录与估算工具。它不提供医疗建议，不诊断疾病，不开饮食处方，也不能替代专业人士。

## 核心思想

FitLog 把三件经常被混在一起的事拆开：

1. 目标阶段：用户是在减脂还是增肌。
2. 基础计算方法：每日目标是 kcal 主导，还是宏量克数主导。
3. 策略层：在基础目标算出后，是否重新分配或复盘碳水。

这种拆分很重要，因为不同用户信任和执行的目标不同。有的人先看 kcal，有的人先看蛋白质/碳水/脂肪克数。如果把两套系统混成一个公式，App 会更难理解，也更容易被误读。

## `energy_ratio`：kcal 优先的计划方式

`energy_ratio` 适合希望把每日 kcal 目标、摄入和剩余量当作主要信号的用户。

它的流程是：

```text
BMR 估算
-> 非运动日常活动基线
-> 减脂赤字或增肌盈余
-> 加上已记录的净运动消耗
-> 按宏量百分比分配最终 kcal 目标
```

为什么需要这个方法：

- 很多饮食计划从能量平衡开始：减脂低于维持，增肌高于维持。
- 当主目标是 kcal 时，宏量百分比容易理解。
- 因为基线有意设定为“非运动日常基线”，所以已记录运动可以作为额外可摄入量加回去。

用户需要知道：

- `diet_goal_phase = cutting` 时，`daily_energy_goal_kcal` 被视为赤字。
- `diet_goal_phase = bulking` 时，`daily_energy_goal_kcal` 被视为盈余。
- 在这个模式下，kcal 目标/摄入/剩余是主计数器。
- 宏量克数由 kcal 目标和宏量百分比换算而来。
- BMR 和活动系数是估算，不是精确测量。

主要证据背景：

- BMR/RMR 估算：`REF-ALG-01`、`REF-ALG-02`。
- 宏量热量换算：`REF-ALG-03`。
- 按热量百分比分配宏量的框架：`REF-ALG-04`。

来源细节和边界见 [References](References.md)。

## `gram_per_kg`：宏量优先的计划方式

`gram_per_kg` 适合希望把蛋白质、碳水和脂肪克数当作主要目标的用户。

它的流程是：

```text
体重
-> 目标阶段
-> 性别选项
-> 粗略训练频率档位
-> 蛋白质/碳水/脂肪 g/kg 表
-> 宏量克数目标
```

为什么需要这个方法：

- 许多训练导向用户会用每 kg 体重多少克来理解蛋白质、碳水和脂肪。
- 蛋白质和碳水需求通常更自然地跟体型和训练背景相关，而不是只跟一个 kcal 数字相关。
- 当用户关心直接吃到多少蛋白质/碳水/脂肪时，宏量优先的显示更容易执行。

用户需要知道：

- `gram_per_kg` 不使用 BMR、活动水平、每日赤字/盈余、已记录运动热量或宏量百分比。
- `training_frequency_per_week` 只是粗略查表档位：每周 2、3、4 或 5 天。
- 这个档位不代表训练强度、训练年限、总训练容量或运动表现需求。
- `prefer_not_to_say` 使用同档位男女平均值。
- 在这个模式下，宏量克数是主目标。
- kcal 是辅助信息，因为 `protein*4 + carbs*4 + fat*9` 只是宏量目标的能量等价值，不是驱动计划的计数器。

为什么这里 kcal 是辅助：

如果 FitLog 先用 g/kg 得到宏量目标，再强行让这些宏量服从另一套独立 kcal 目标，两套系统就可能互相打架。用户会看到宏量目标指向一个方向，kcal 计数器又指向另一个方向。FitLog 通过让宏量克数成为 `gram_per_kg` 的来源，避免这种混乱。

主要证据背景：

- 宏量热量换算：`REF-ALG-03`。
- 蛋白质 g/kg 范围和运动营养背景：`REF-ALG-05`、`REF-ALG-06`。
- 饮食与身体成分框架：`REF-ALG-07`。

## 为什么两种饮食模式不能混算

两个模式回答的是不同问题。

`energy_ratio` 问的是：

```text
给定我的 kcal 目标，我应该吃多少克蛋白质/碳水/脂肪？
```

`gram_per_kg` 问的是：

```text
给定我的体重和训练背景，我应该瞄准多少克蛋白质/碳水/脂肪？
```

两者都可能有用，但不应该同时控制同一个目标。FitLog 保持它们分离，是为了让用户始终知道哪个数字才是主目标。

## 碳循环

`carb_cycling` 是减脂期策略层。它在基础目标已经算出后，重新分配一周碳水。

它的流程是：

```text
基础碳水
-> 选择 high / medium / low 日
-> 归一化 7 天倍率
-> 某些天提高碳水，某些天降低碳水
-> 控制每周平均碳水
```

为什么需要这个方法：

- 有些用户希望训练较难的日子多吃碳水，轻松日或休息日少吃碳水。
- 碳水需求会随训练需求变化。
- 每周归一化能避免“看似循环，实际偷偷整体吃多”或“整体压得过低”。

用户需要知道：

- 碳循环不是神奇燃脂算法。
- 如果每周总摄入和执行度不好，它不会自动带来更好结果。
- 它保持蛋白质和脂肪稳定，主要调整碳水。
- 它有安全下限：碳水不应低于 `max(weightKg * 1.2, 100)`。
- 如果触发下限，FitLog 会 clamp 目标并记录本地 reason code。

主要证据背景：

- 周期化碳水可用性：`REF-ALG-13`。
- 周期化碳水限制证据边界：`REF-ALG-14`。
- 碳水需求随训练需求变化：`REF-ALG-15`。

## 碳水渐降

`carb_tapering` 是减脂期的本地复盘策略。它不会替用户自动节食。

它的流程是：

```text
复盘近期体重趋势
-> 检查饮食记录覆盖率
-> 检查训练稳定性
-> 比较当前减重速度和目标区间
-> 建议保持、减少碳水、暂停 taper 或不操作
-> 等待用户确认
```

为什么需要这个方法：

- 减脂过程中常常需要小幅调整。
- 体重会受到水分、食物体积、钠、消化和训练压力影响。
- 滚动复盘比根据单日体重反应更稳妥。
- 用户确认可以避免 App 悄悄把计划越收越紧。

用户需要知道：

- FitLog 看滚动趋势，不看单次称重。
- 饮食记录覆盖率很重要，因为记录不足会让趋势难以解释。
- 训练稳定性很重要，因为训练明显下降时，激进减碳可能不合适。
- 建议的碳水变化是小步调整，不是自动惩罚。
- 如果数据不足，App 应该给出 `no_data`，而不是假装知道。
- 如果减重过快，App 可以建议 `pause_taper`。
- 如果碳水会低于安全下限，App 会阻止继续下降。

主要证据背景：

- 训练阶段的蛋白质保留：`REF-ALG-16`。
- 保守减重速度框架：`REF-ALG-17`。
- 备赛宏量变化观察：`REF-ALG-18`。
- 动态体重变化限制：`REF-ALG-19`。

## 为什么运动消耗使用净消耗

FitLog 会把已记录运动消耗加到 `energy_ratio` 的可摄入目标里。为了避免重复计算，这个运动消耗必须是“额外净运动消耗”。

原因很简单：

每日基线已经包含身体在那段时间即使休息也会消耗的热量。如果 FitLog 直接加上总运动消耗，而不扣除静息消耗，就会把同一份静息热量算两次。

有氧计算使用：

```text
netMet = max(0, MET - 1)
netCardioKcal = netMet * 3.5 * bodyWeightKg / 200 * durationMinutes
```

为什么减去 1 MET：

- 1 MET 大致代表静息能量消耗。
- 非运动基线已经包含静息代谢。
- 减去 1 MET 是为了估算“做这个活动相比休息多消耗了多少”。

例子：

如果某活动是 8 MET，FitLog 会把额外运动成本近似看作 7 MET，而不是 8 MET，因为最初的 1 MET 已经在每日基线里了。

主要证据背景：

- MET 数值和换算：`REF-ALG-08`、`REF-ALG-09`。

## 为什么力量训练不简单按分钟计算

力量训练不适合简单建模为每分钟多少 kcal。

原因：

- 60 分钟力量训练可能包含重组、轻组、热身和很长的组间休息。
- 两次时长相同的训练，负荷、次数和总训练量可能完全不同。
- 线性按分钟计算会高估休息时间，也会低估真正的训练工作。

FitLog 使用训练量和动作类型：

```text
有效负荷
-> 次数
-> 总训练量
-> 动作 profile 系数
-> 主动举铁消耗
-> 恢复和适应成分
```

时长仍然有作用，但只作为有上限的恢复密度修正。它可以让更密集和更慢的 session 出现小幅差异，但不会线性增加热量。

用户需要知道：

- 力量消耗估算是启发式。
- 它适合在 FitLog 内保持一致，不是实验室级测量。
- App 优先避免明显重复计算，而不是假装能精确知道运动消耗。

## 为什么 FitLog 使用边界和用户确认

FitLog 使用本地确定性规则和用户确认，是因为输入数据本身并不完美。

重要的不确定来源：

- 餐食估算可能有误差。
- 外部 AI 估算可能有误差。
- 体重变化可能来自水分、食物体积、钠、训练压力或消化状态。
- 运动消耗估算是近似值。
- BMR 和活动系数是人群估算。

FitLog 对不确定性的处理方式：

- 保持计算模式分离
- 使用滚动窗口，而不是单日反应
- clamp 不安全或极端数值
- carb taper 必须由用户确认
- 展示策略 reason/context，而不是隐藏它
- 除非真正实现 AI，否则不声称 App 内有 AI
